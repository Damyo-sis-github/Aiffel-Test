## 리뷰 중 발견하고 수정한 결함

체크리스트를 돌리는 과정에서 실제로 잡힌 것들입니다. 전부 재현 테스트를 붙였습니다.

### 1. [치명] 합성 데이터의 슬라이스 불변성 붕괴 — RNG 스트림 오프셋

`app/data/adapters/synthetic.py`

**증상**: 같은 종목의 같은 날짜 가격이 **조회 종료일에 따라 달라졌습니다.**
ARKX 2020-06-02 종가가 조회일에 따라 95.62 / 51.57 / 343.13 / 79.45 로 나왔습니다.

**원인**: 하나의 `Generator` 에서 길이가 `n` 인 배열을 연달아 뽑았습니다.

```python
switch = rng.random(n)          # 앞 배열이 스트림을 n 만큼 소비
ret = rng.normal(mus[state], vols[state])   # → 뒤 배열의 시작 오프셋이 n 에 의존
```

`end` 가 바뀌면 `n` 이 바뀌고, 그러면 **과거 날짜의 값까지 전부 달라집니다.**

**파급**: NAV 가 하루 만에 100M → 59M → 50M → 94M 로 요동쳤고, 킬스위치가 3일차에 41% 낙폭으로
오발동했으며, 익스포저 상한이 2.6배·4.6배로 뚫렸습니다. 전부 이 하나에서 나온 2차 증상이었습니다.

**수정**: 고정 지평(ANCHOR~2027-12-31) 전체를 생성한 뒤 잘라내고, **난수 배열마다 독립된 생성기**를 씁니다.

**교훈**: 이 등급의 버그는 예외를 던지지 않습니다. 그럴듯한 숫자를 만들 뿐입니다.
합성 데이터에서 났기에 망정이지, 실데이터 어댑터의 캐시 계층에서 같은 실수를 하면 알아채기 어렵습니다.

### 2. [치명] 페이퍼 파이프라인에 청산 로직 부재

`app/pipeline/daily.py`, `app/pipeline/positions.py` (신규)

**증상**: 포지션이 열리기만 하고 **한 건도 청산되지 않았습니다.** 리포트가 계속 "청산 거래 없음"만 찍었습니다.

**파급**: 백테스트 엔진에는 손절·호라이즌·최대보유·상폐 청산이 전부 있었지만 페이퍼 경로에는 없었습니다.
그 결과:
- W_trade / 기대값이 **영원히 계산되지 않습니다** → 게이트 2·8 판정 불가
- T1 트리거(성과 미달)가 영원히 발동하지 않습니다 → 자가발전 루프 자체가 죽습니다
- 익스포저가 단조 증가해 상한에 계속 부딪힙니다

**수정**: `app/pipeline/positions.py` 를 만들어 엔진과 **동일한** 하드 제약을 적용합니다
(상폐 → 장중 손절 → 보유기간). `PaperBroker.close()` 가 실현 거래를 반환하고 `trades` 테이블에 들어갑니다.

수정 후 55거래일 실행: 청산 183건, W_trade 51.4%, E −0.82%, 손절 23건.

### 3. [높음] LEV/INV 가 6거래일 보유됨 — 청산 주문의 t+1 한 칸

`app/backtest/engine.py`

**증상**: `#19` 테스트가 최대 보유 11일(달력)을 잡았습니다. 거래일 기준으로는 6일이었습니다.

**원인**: `horizon_due_ord = _offset_ord(symbol, day, 5)` 로 5번째 바에 청산을 **예약**했는데,
청산 주문은 t+1 에 체결되므로 실제 보유는 6거래일이 되었습니다.

**수정**: `_due_ord()` 를 도입해 `hold_bars - 1` 번째 바에 예약합니다. `hold_bars` 컬럼을 추가해
거래일 기준으로 검증하도록 테스트도 바꿨습니다(달력일 기준 검증은 휴일 때문에 무의미했습니다).

### 4. [높음] 자본 배분의 계열 상한이 재정규화로 무력화

`app/portfolio/allocation.py`

**증상**: 계열 상한 50% 를 걸었는데 LONG 계열이 71.4% 를 받았습니다.

**원인**: `_cap_by_group` 으로 축소한 뒤 마지막에 `w / total` 로 정규화하면서 축소분이 도로 부풀었습니다.

**수정**: 정규화 → 종목 상한 → 계열 상한을 **한 루프 안에서** 수렴할 때까지 반복하고,
축소로 풀린 몫은 여유 있는 계열에 비례 배분합니다.

### 5. [중간] 과거 날짜 재실행 시 이후 스냅샷이 무효화되지 않음

`app/pipeline/state.py`

**증상**: 1일 → 2일 → 3일 실행 후 1일을 재실행하면, 2·3일 스냅샷이 그대로 남습니다.
나중에 3일을 재실행하면 **낡은 상태로 되돌아가** 조용히 틀린 결과가 나옵니다.

**수정**: `prepare()` 가 스냅샷을 복원할 때 그 이후 날짜의 스냅샷을 지웁니다. 재현 테스트 추가.

### 6. [중간] 청산 주문이 휴장일에 폐기됨

`app/backtest/engine.py`

**증상**: `pending` 리스트에서 체결 불가 주문을 전부 버렸습니다. 진입 신호는 폐기가 맞지만(§7.3),
**청산 주문을 폐기하면 포지션이 영원히 남습니다.**

**수정**: `action == "close"` 인 주문은 거래 가능한 첫 바까지 들고 갑니다.
같은 포지션에 청산 주문이 매일 중복 예약되던 문제도 `exit_pending` 플래그로 막았습니다.

### 7. [중간] 경로 가드가 다른 OS 에서 무력화

`app/guards/path.py`

**증상**: `Path(r"C:\Users\me\OneDrive\quant").resolve()` 가 리눅스에서 cwd 를 앞에 붙여
OneDrive 동기화 루트 검사가 통과했습니다.

**수정**: 실제 존재하는 경로만 `resolve()` 합니다.

### 8. [낮음] SQLite 롤백이 원래 예외를 가림

`app/data/meta_db.py`

`executescript` 이후 트랜잭션이 없는 상태에서 `ROLLBACK` 을 호출해 `OperationalError` 가 나고,
그것이 진짜 원인(타입 바인딩 실패)을 완전히 덮었습니다. `in_transaction` 확인 + `suppress` 로 수정.

### 9. [낮음] 예측 날짜가 JSON 왕복에서 Timestamp 로 변해 SQLite 바인딩 실패

`pd.read_json` 이 `pred_date` 를 자동으로 Timestamp 로 바꿔 `sqlite3.ProgrammingError` 가 났습니다.
`_normalize_predictions()` 로 타입을 고정했습니다.

## 남은 우려 (수정하지 않음, 판단 필요)

1. **익스포저 상한은 진입 시점 검사입니다.**
   진입 후 가격이 움직여 NAV 가 줄면 비율이 사후에 상한을 조금 넘습니다.
   명세 §8.2 가 "리스크 체크는 신호 후·주문 전"이라 설계대로지만, 실전에서는
   장중 강제 축소가 필요할 수 있습니다. 지금은 리포트에만 드러납니다.

2. **조정가 누출.** yfinance 는 시점별 `adj_factor` 를 주지 않고 오늘 기준 하나만 줍니다.
   피처를 전부 비율로 만들어 대부분 상쇄했지만, `adj_factor` 자체가 시간에 따라 갱신되는 구조가 아닙니다.
   완전한 해결은 매일의 `adj_factor` 를 별도 시계열로 적재하는 것입니다(Phase 4).

3. **KR 휴장일 테이블이 미검증 시드값입니다.**
   틀리면 백테스트가 조용히 어긋납니다. 그래서 `verified: false` 동안 캘린더 게이트를
   중단이 아니라 플래그로 강등했지만, 이건 문제를 미루는 것이지 푸는 것이 아닙니다.
   실데이터 투입 전 `quant calendar --refresh-kr` 이 **필수**입니다.

4. **B_pred 를 최근 60일 표본으로 근사합니다.** 계산 비용 때문이며 리포트에 명시되지 않습니다.
   표본 기간이 편향되면 W_pred − B_pred 의 해석이 흔들립니다.

5. **`_last_cycles()` 가 참조하는 `cycle_complete` 로그를 아직 아무도 쓰지 않습니다.**
   `/evolve` 슬래시 커맨드가 이를 기록해야 쿨다운이 실제로 작동합니다. 지금은 쿨다운이
   사실상 비활성입니다. 첫 진화 사이클을 돌릴 때 반드시 확인해야 합니다.

6. **합성 데이터에서 일부 시드 전략이 0거래입니다** (`h5_breakout_vol`, `h5_inv_regime`).
   합성 데이터가 거래량 2배 급증이나 하락 레짐을 거의 만들지 않기 때문입니다.
   실데이터에서 다시 확인해야 하며, 그때도 0거래면 조건이 너무 좁은 것입니다.

7. **`--skip-guards` 가 CLI 에 노출되어 있습니다.** 개발용이지만 실운영에서 습관적으로 쓰면
   #31·#33·#34 가 전부 무력화됩니다. 리포트 배너가 없으므로(`QUANT_GUARD_BYPASS` 만 배너가 붙음)
   Codex 리뷰에서 이 지점을 다시 봐 주십시오.

## Codex 리뷰 시 특히 봐 주었으면 하는 곳

우선순위 순입니다.

1. `app/backtest/engine.py` — 일별 루프의 순서(A~F)가 룩어헤드 없이 맞는가.
   특히 `_exposure_ok` 가 같은 날 여러 주문을 처리할 때 누적을 제대로 반영하는가.

   두 경로가 갈라지면 백테스트와 페이퍼의 괴리로 나타나고, 그 괴리를 전략 탓으로 오진하게 됩니다.

4. `app/features/price.py` — "비율만 쓴다"는 주장이 실제로 모든 피처에서 지켜지는가.
5. `app/evaluator/` 전체 — 게이트가 실제로 명세 §7.5·§7.6 표와 일치하는가.
6. `app/pipeline/daily.py` `run()` — 결과 해시에 들어가는 항목이 재현성을 보장하기에 충분한가.
